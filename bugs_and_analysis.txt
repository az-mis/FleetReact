1. Project Architecture & Overview
Tech Stack & Structure
•	Frontend: React 18, TypeScript, Vite, React Router DOM v6, Lucide Icons.
•	Backend / Database: Firebase Authentication, Cloud Firestore, Firebase Hosting/Netlify.
•	Asset Storage: Google Drive API via Google Identity Services (gis) OAuth2 token flow.
•	Architecture Style: Serverless single-page application (SPA). Client communicates directly with Firestore and Google Drive without an intermediate custom backend API server.

2. Security Vulnerability & Risk Assessment
1. High Risk: Firestore User Enumeration & Partial Rule Mismatches
•	Observation: In firestore.rules, regular admins are allowed to create users if request.resource.data.role == 'driver'. However, in the client side (Admins.tsx), admins can create other admin accounts. If a regular admin calls createUserWithoutSignIn with role admin, the write rule will reject the document write, leaving an orphaned Firebase Auth user without a Firestore user document.
•	Impact: Orphaned auth accounts and potential denial of service / state mismatch.
•	Defensive Recommendation: Enforce admin creation logic solely for super_admin in client UI and ensure backend/rules enforce that regular admin cannot manipulate role fields.
2. Medium Risk: Public Read Access on Vehicle Availability & Document IDs
•	Observation: firestore.rules allows public get for single documents in vehicleRequests using the reference code. In RequestVehicle.tsx, the reference code is 7 characters chosen from a 30-character alphabet (≈307≈21.8 billion≈307≈21.8 billion combinations).
•	Impact: While 21.8B is reasonably large, lack of rate-limiting at the Firestore level allows high-throughput automated guessing if not paired with App Check.
•	Defensive Recommendation: Enable Firebase App Check (reCAPTCHA Enterprise) on public requests to prevent automated scraping.
3. Medium Risk: Direct Public Client-Side User Creation via Secondary App
•	Observation: In src/lib/secondaryAuth.ts, account creation is handled by instantiating a temporary Firebase app on the client side with createUserWithEmailAndPassword.
•	Impact: Any authenticated user or compromised client session can attempt to trigger arbitrary Firebase Auth user registrations directly on the project's Auth tenant.
•	Defensive Recommendation: Transition user provisioning to a secure backend endpoint / Cloud Function leveraging the Firebase Admin SDK (admin.auth().createUser()) gated strictly to super_admin or admin.
4. Low/Operational Risk: Google Drive Public File Sharing
•	Observation: In src/lib/googleDrive.ts, uploaded images are automatically shared as role: "reader", type: "anyone".
•	Impact: Anyone who discovers or guesses the Google Drive thumbnail URL can view profile photos or vehicle images without authentication.

3. Code Quality, TypeScript & Bug Analysis
1. Build Type Incompatibility with Lucide React Icons (Resolved)
•	Bug Found: In multiple files (src/components/Avatar.tsx, src/pages/VehicleRequests.tsx), icon props were typed as React.ComponentType<{ size?: number }> instead of LucideIcon from lucide-react. This triggered TypeScript compilation failures (TS2322: WeakValidationMap types are incompatible).
2. Denormalized State Synchronization Gaps
•	Bug / Inconsistency:
•	When a driver is deleted in Drivers.tsx, existing vehicles assigned to that driver still retain assignedDriverId and assignedDriverName in the vehicles collection.
•	When an assigned vehicle is deleted in Vehicles.tsx, active pending or approved vehicle requests still reference that vehicleId.
•	Remediation: Implement cascading cleanup in batch writes or Cloud Function triggers upon document deletion.
3. Missing Unsaved Photo Cleanup on Cancelled Form Submissions
•	Observation: If an image is selected and staged in forms, the local blob preview is maintained; if an upload fails midway or is cancelled, temporary references must be cleaned up to avoid memory leaks.
